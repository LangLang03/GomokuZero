## 2. 已修复的 P0 级问题

### P0-01 Arena MCTS 评估了错误的局面

`select_leaf()` 先把根局面复制进 `task.board`：

```cpp
task.board = game.board;
```

然后沿搜索路径逐层 `task.board.play(child.action)`，因此需要送进网络的是
**叶节点**的 `task.board`。但 `ArenaSearch::run()` 实际写的是：

```cpp
game.board.encode_state(state.data());   // game.board 始终是根
```

后果：同一根局面的网络输出被重复用于不同深度的所有叶节点，MCTS 评估完全失真，
`candidate vs baseline` 的胜负不能作为棋力指标。

修复后 `task.board.encode_state(...)`。

**回归测试**：`gomoku_regression` 验证不同叶局面编码不同、且网络输出对其有响应。

### P0-02 KL 诊断污染训练轨迹

原实现为了测量策略移动量，自己执行了一次 `train_step()`：

```
forward(before) -> train_step(lr*0.1) -> forward(after) -> KL
```

每 5 个 batch 调用一次，于是每 5 批就多出一次优化步，同时推进 Adam 动量与
step 计数、更新 BN running statistics。**开启/关闭诊断会得到不同模型。**

修复：在正常 `policy_update()` 前后各采一次同一 probe batch 的前向，
诊断变成纯观测：

```
update_kl_probe()          // forward(before)
policy_update(i)           // 正常训练
log_true_kl(i)             // 用 policy_update 内记录的 after 计算
```

**回归测试**：连续两次 `forward_one` 必须逐位相同（无隐藏更新）。

### P0-03 checkpoint 语义

折合 BN 对推理是精确等价变换，但改变了参数化：折合后 BN 的
`gamma/beta/running_mean/running_var` 不复存在，网络只是"函数等价"，
`running_var` 被重置为 `1-eps`，若继续训练则统计量从头累积。

现在分两种形式：

| 形式 | 内容 | 用途 |
|---|---|---|
| **推理导出** | 折合后的 conv weight/bias + FC | MCTS、`human`、部署、CPU 推理 |
| **训练 checkpoint** | 原始 conv weight/bias + BN gamma/beta/running stats + FC + batch index（+`training.meta`） | 续训 |

`load_native()` 通过 `training.meta` 是否存在自动识别两种形式；训练形式会从原始
张量重建折合缓冲，因此 `--cpu` 切过去依然正确。`evaluate_and_save()` 写训练形式。

### P0-04 / P1-01 policy target 给非法格分配概率

```cpp
// 旧: spread = smooth / 225, 覆盖全部格子
// 新: spread = smooth / legal_count, 只覆盖空位, 占用位强制为 0
```

`train.cpp` 的人类棋谱平滑同样改为基于 state 的 occupancy mask
（通道 0/1 持有双方棋子）。

**回归测试**：`gomoku_regression` 检查占用格概率恒为 0、合法格均有质量、总和为 1。

## 3. P1-06 的实测结论：TF32 无需修改

报告建议把 TF32 做成可配置项以换取吞吐。实测（RTX 5060 Laptop，
12 层 × 192 通道，batch=128）：

| 精度 | ms/call | eval/s |
|---|---:|---:|
| full FP32（当前） | 49.47 | 2588 |
| TF32 | 50.54 | 2533 |

**TF32 反而略慢**，因此为 parity 禁用它的代价为零。已在
`CudaNetworkBackend::forward()` 注释中记录该测量结果，避免后人重复"优化"。

## 5. P1-07 修复：CUDA batch 目标重新实测

原常量 `CUDA_TARGET_BATCH = 128` 来自旧 3 层网络的 benchmark，不能继承。
对当前主干扫描：

| batch | 16 | **32** | 64 | 96 | 128 | 192 | 256 | 512 |
|---|---:|---:|---:|---:|---:|---:|---:|---:|
| eval/s | 2710 | **2846** | 2301 | 2435 | 2588 | 2295 | 2076 | 2062 |

最优点为 **32**。已改为可配置 `--inference-batch`（默认 32）。

自对弈实测收益：

| | s/game | moves/game | evals | calls | avg_batch | cache 命中 |
|---|---:|---:|---:|---:|---:|---:|
| batch 目标 128 | 7.30 | 46.7 | 501,216 | 4,468 | 112.2 | 13.9% |
| batch 目标 **32** | **6.26** | 45.9 | 500,884 | 16,979 | 29.5 | 12.1% |

**每局 7.30 s → 6.26 s（快 14%）**。

## 6. 报告第 4 节的感受野数值：已确认并修正

报告指出"25 层 3×3 卷积 → RF = 1 + 25×2 = 51"，并指出我此前写的
"25×25"不准确。**报告正确。**

实际计数：`1` 个 stem + `12 × 2` 个残差卷积 = 25 个 3×3 卷积，
每层使感受野直径 +2，故 `RF = 1 + 25 × 2 = 51`。

`tests/backend_parity.cpp` 已据此调整断言（要求覆盖棋盘而非固定 25），
README 中的表述也改为"25 层卷积，覆盖全盘"。
