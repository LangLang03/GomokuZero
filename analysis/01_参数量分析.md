# 问题分析 1：参数量不足

分析对象：`best_policy_scratch_50mix_v2_bin` / `best_policy_scratch_50mix_v3_bin`
（两者参数量完全相同）
分析方法：读取 16 个 `.bin` 权重文件做精确计数 + 在真实人类棋谱局面上跑逐层前向统计
（512 个局面，平均 31.4 手）+ PyTorch autograd 感受野验证。

---

## 结论速览

**"参数量太少"这个判断成立，但根因不是"总数该放大 N 倍"，而是三件事叠加：**

| # | 问题 | 量化结果 | 严重度 |
|---|---|---|---|
| 1 | 有效感受野小于五连判定所需 | 主干感受野 **7×7**，判定五连最少需要 **9×9** | 致命（结构缺陷，加参数治不好） |
| 2 | 容量放错了地方 | **62.4%** 的参数在策略头，主干只占 **28.7%** | 高 |
| 3 | 主干通道实际利用率低 | conv3 有 **15.6%（20/128）通道全零死掉** | 中高 |

另外发现一个伴随问题：`train.cpp` 里 `lr_multiplier_ < 2,0` 是**逗号表达式**（永远为假），
学习率乘数只能降不能升。这会造成后期学习率塌陷，进一步让"参数训不动"表现为容量不足。
详见后续的算法问题分析。

### 容量分配极不均衡

```
共享主干   93,536   28.7%     <- 唯一的特征提取器，也是泛化的来源
策略头    203,241   62.4%     (其中 fc 900->225 一项就占 62.1%)
价值头     29,187    9.0%     <- 价值是策略的"裁判"，容量只有策略的 1/7
```

**这个比例是反的。** 一个 15×15 棋盘的决策质量取决于主干能否提取出
"活三 / 冲四 / 双三 / 禁手"这些局部形状。主干只有 9.4 万参数
（其中 3×3 核本体 93,312，偏置 224），却要承担：

- 4 个输入通道 → 3 个尺度（4→32→64→128）的特征抽象
- 为策略和价值两个任务共享
- 泛化到约 10^40 量级的合法局面空间

而策略头那 20 万参数里，绝大部分是在做一件**没有空间归纳偏置**的工作
（见第 3 节）。

## 2. 致命问题：感受野只有 7×7，判定不了五连

主干是 3 层 3×3（`padding=1`），理论感受野半径 = 2×3+1 = 7。

用 PyTorch autograd 在等价结构上数值验证（扰动中心格，回传看哪些输入格有梯度）：

```
行范围 4..10  列范围 4..10  ->  受影响输入格数 = 49 = 7x7   （理论值一致）
```

**为什么这是致命的：** 判定一个落点是否构成五连，必须看到**半径 4**的整条线
（落点 + 左右各 4 格）。落子在中心 (7,7) 时，需要看到列 3..11 共 9 格，
而当前主干**看不见** `(7,3) (7,4) (7,10) (7,11)` 这 4 个位置。

后果：

- **长程威胁完全不可见。** 例如 `(7,4)(7,5)(7,6)` 是一个活三，落 `(7,7)` 成四、
  落 `(7,3)` 或 `(7,8)` 成活四 —— 但落在 (7,7) 的输出通道感受野里根本没有 (7,3) 的信息。
- **地平线效应。** 网络只能看到"3 步以内"的局部，无法区分"自己的三在延长"
  和"对方的三在旁边"，除非这个区分恰好落在 7×7 窗口里。
- **加宽加参数量治不好。** 把通道从 128 加到 512，只是让 7×7 窗口内的表达更细，
  窗口外的信息依然进不来。

### 主干有效容量核算

93,536 个主干参数，扣掉通道缩放（32→64→128）这个"免费"部分后，
真正编码局部模式的是 3×3 核本体：93,312 个权重 = **10,368 个 3×3 卷积核**。

五子棋局部形状空间（3×3 窗口、每格 {空/黑/白}，去掉对称）量级是 10^3~10^4，
看上去 10,368 个核"够用" —— 但这 10,368 个核要在**3 个级联层**里同时承担
形状检测 + 颜色对称性 + 威胁等级排序 + 4 个方向的组合，而且第 1 层的 32 个通道
要消化全部 4 个输入通道的所有基础形状。实际结果是欠拟合，有直接证据：

```
在 512 个真实人类棋谱局面上：
  conv1(32ch)   激活率 38.73%   死通道  0.0%  ( 0.0/32)
  conv2(64ch)   激活率 33.32%   死通道  1.6%  ( 1.0/64)
  conv3(128ch)  激活率 42.88%   死通道 15.6%  (20.0/128)   <-- 20 个通道完全没参与学习
```

主干最后一层 128 个通道里有 20 个在真实数据上**恒为 0**：
这 20×64×9 = 11,520 个权重（占主干 12.3%）从没收到过有效梯度。
这不是"参数不够"，而是"参数死了"——根因是缺少 BatchNorm / 残差连接，
3 层普通 conv+ReLU 堆叠容易出现通道塌缩。

## 3. 容量放错位置：策略头 62% 的参数用在了错误的地方

### 3.1 结构违反局部性

```
policy: conv1x1 128->4 relu -> fc 900->225 -> log_softmax
```

`conv1x1(128→4)` 把 128 通道压成 4 个"每格特征"，然后 `fc(900→225)`
**把整张棋盘的 225 个格子展平后全连接**。实测每个输出单元都依赖全部 225 个输入格：

```
每个输出实际依赖的输入格数: 平均 225.0 / 225
```

也就是说，该层**完全没有权重共享、没有平移等变性**。位于 (0,0) 角的输出和
位于 (7,7) 中心的输出使用**互不相关的 900 个权重**，各自独立学习。
模型必须自己从零学出"局部形状"这个概念 225 遍，而且无法把中心学到的规则
迁移到边角。

标准做法（AlphaGo Zero / AlphaZero / 各类五子棋实现）是：
`conv1x1 128->2 -> reshape(2*225) -> fc(2*225->225)`，
即**先用共享的 1×1 卷积产生每格 2 个 logit，再用一个 450→225 的小全连接做全局混合**。
这样参数从 202,500 降到 450×225 = 101,250，而且局部模式在 225 个位置上共享。

### 3.2 前向时 70% 的输入是零

`pa = relu(conv1x1(c3))` 的激活率实测：

```
在真实棋谱局面上: pa 每步非零单元 平均 269 / 900 (中位 237, 范围 150-429)
                -> 每步真正被激活的输入子空间只有 29.9%
```

`act_fc1_weight` 有 202,500 个权重，每个状态前向时只有约
202,500 × 0.299 ≈ **60,500 个权重参与贡献**，其余 14 万乘的是 0。
配合 fc 层没有 weight decay（`Adam(..., weight_decay=0.0)`），
这些长期乘 0 的权重只能靠 Adam 的初始化噪声随缘移动。

### 3.3 棋盘边缘几乎没有信号

- 第 0 行 / 第 14 行 / 第 0 列 / 第 14 列只有 **~50%** 有信号，

  但对全连接的策略头是叠加伤害：**边缘位置的 900 维权重的有效训练信号
  只有中心位置的一半**，而边缘位置在 15×15 上有 56 个（24.9% 的格子）。

后果叠加：策略头 62% 的参数里，有相当一部分（边缘对应的行 + 恒零输入对应的列）
处在**信噪比极低**的状态。

### 3.4 输出分辨率被 tanh/无界 logit 放大

```
plogit 动态范围: 平均 20.585 (中位 20.919)
输出熵: 平均 2.889 nats  (均匀分布 5.416)
top1 概率: 0.306
```

logit 范围 20 意味着 softmax 输出极端尖锐。这本身不是容量问题，
但它说明策略头在用**极高的置信度**做判断——如果主干只看到 7×7，
这种高置信度是危险的（对未见过的长程威胁会给出高置信度的错答）。

## 4. 与标准规模的对比

| 方案 | 主干 | 策略头 | 价值头 | 总计 | 主干占比 |
|---|---:|---:|---:|---:|---:|
| **当前（3 层, 4→32→64→128）** | 93,536 | 203,241 | 29,187 | **325,964** | 28.7% |
| 6 层 × 96ch | 418,752 | 203,113 | 29,123 | 650,988 | 64.3% |
| 8 层 × 128ch | 1,037,824 | 203,241 | 29,187 | 1,270,252 | 81.7% |
| 10 层 × 160ch | 2,080,960 | 203,369 | 29,251 | 2,313,580 | 89.9% |
| 12 层 × 192ch | 3,658,752 | 203,497 | 29,315 | 3,891,564 | 94.0% |

注：表中策略头仍沿用当前的 `fc 900->225`；若改成标准的 `1x1→2ch + fc 450->225`，
策略头降到约 101,700，总参数再减 10 万左右。

即使按最激进的 **12 层 × 192ch（3.89 M 参数）**，也只有当前规模的 **11.9 倍**。
对一张 RTX 5060（8 GB）和 2.6 GB 的本地棋谱数据来说，这个规模完全在射程内。
当前 325,964 参数搭配 72.8 万条棋谱样本 + 每轮约 3000 条自对弈样本，
**参数量相对数据量是明显偏小的**。

## 5. 数据侧旁证：为什么"少参数"没被数据量掩盖

- 人类棋谱实际样本数 **364,021**（不是文件里的 728,042 —— u64 头的元素总数除以 225
  才是样本数；见 `tools/npz_to_bin.py` 的 `struct.pack('<Q', arr.size)`）。
- 自对弈：79 批 × 64 局 ≈ 5,056 局 × 每局约 40 手 ≈ 20 万状态，
  经 `buffer_size=10000` 的环形缓冲后，每批只随机抽 `batch_size=512` 中的 256 条。
- 人类棋谱目标分布实测：**平均非零项 = 1.0**（one-hot，`parse_renjunet.py:76`
  `p[moves[k+1]] = 1.0`），熵 **0.000 nats**。

也就是说：自对弈给的是软分布（MCTS 访问计数），人类棋谱给的是**硬 one-hot**，
两者混在同一个 batch 里（`--mix-ratio 0.5`）。用 one-hot 训练时，
交叉熵会以极高置信度惩罚其余 224 个合法落点——**这正是策略头需要
"记住每个局面唯一答案"的用法，是最吃参数量的训练信号**。
325,964 参数去拟合这种目标，容量不足会被放大成明显的过拟合/欠拟合摇摆。

（这条同时指向后续要单独分析的"算法/数据问题"，此处只作为参数量结论的旁证。）

## 6. 建议的修改方向（按性价比排序）

### P0 —— 修感受野（不改参数量级也能获益）

把主干从 3 层改成 **6 层**（感受野 13×13，完整覆盖五连判定）或者
**5 层 + 1 层 dilation=2**（感受野 15×15）。这是**唯一必须改**的结构项。

### P1 —— 把参数从策略头搬到主干

```
当前:
  conv3x3 4->32 -> conv3x3 32->64 -> conv3x3 64->128
  policy: conv1x1 128->4 -> fc 900->225
建议:
  主干: conv3x3 4->64 -> [res block 64] x 5      (感受野 13x13)
  policy: conv1x1 64->2 -> fc 450->225
  value:  conv1x1 64->1 -> fc 225->64 -> fc 64->1 -> tanh
```

预期总参数约 **44 万**（比现在多 35%），但主干占比从 28.7% 提到 **~75%**，
策略头从 20 万降到 10 万。

### P2 —— 加残差 + BatchNorm

解决实测到的 `conv3` 15.6% 死通道问题。残差连接让梯度直达浅层，
BatchNorm 让通道激活分布稳定。这两者在手写反向传播里工作量不小，
但如果没有，加深网络会立刻遇到训练不动的问题。

### P3 —— 若继续放大，注意同步点

网络形状目前在两处**手工重复定义**，改结构必须同步：

- `src/network.h:66-70`（CPU 的 ConvLayer/FCLayer 成员）
- `src/network_cuda.cpp:16-23`（LibTorch 的 Conv2d/Linear 定义）
- `tests/dump_forward.cpp`、`tools/export_onnx.py:19-21` 也各自硬编码了形状

建议先抽一个共享的 `NetConfig` 常量表，否则改完必然出现 CPU/CUDA/ONNX 三端不一致。
