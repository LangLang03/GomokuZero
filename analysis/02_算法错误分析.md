# 问题分析 2：算法错误

分析对象：编译产物实际包含的 7 个源文件（见 `CMakeLists.txt:41-49`）
复现：实测训练 30 批，`GOMOK_SEED=7 --mix data/mix_data --mix-ratio 0.5`
（完整日志见文末附录）

## 结论速览

**2 个严重缺陷 + 3 个中等缺陷 + 7 个工程问题。**

最严重的一条不是任何单点 bug，而是：
**训练 30 批后，验证指标完全停滞（val_loss 3.708 → 3.633，top1 30.3% → 33.0%），
而学习率乘数已经开始不可逆衰减。**

| 级别 | 问题 | 位置 | 后果 |
|---|---|---|---|
| **P0** | 用"相邻批次 loss 差"冒充 KL 散度，驱动学习率单调衰减 | `train.cpp:135-148` | 30 批内 lr× 从 1.0 掉到 0.132；79 批会撞 0.01 下限 |
| **P0** | `mix_ratio=0.5` 的语义陷阱：混合数据利用率仅 **0.03 次/样本** | `train.cpp:87-126` | 69 万条人类棋谱实际只用到 3% |
| **P1** | 缺少 Dirichlet 根噪声 + 温度调度 | `selfplay.cpp:428-807` | 自对弈多样性不足，探索退化 |
| **P1** | `MAX_CAND=40` 截断 → 82.5% 的位置被标成"绝不可下" | `selfplay.cpp:28,356` | 策略目标与真实棋理矛盾 |
| **P1** | 验证指标是"拟合人类 one-hot 的 top1"，不是棋力 | `train.cpp:158-191` | 无法判断模型好坏 |
| **P2** | `weight_decay=0`（CPU）/ `0.01`（CUDA）不一致 | `optimizer.h:12`, `network_cuda.cpp:85` | 两后端训出不同模型 |
| **P3** | 无数据增强、无最佳模型选择、日志不落盘等 | 多处 | 见第 6 节 |

## 1. 【P0】学习率自适应完全失效，30 批内衰减到 1/8

### 1.1 代码

```cpp
// train.cpp:135-148
// Approximate KL by the change in loss, smoothed to reduce noise.
static float prev_loss = 0;
static float smoothed_kl = 0.05f;
const float raw_kl = prev_loss > 0 ? std::abs(stats.loss - prev_loss) : 0.05f;
smoothed_kl = 0.7f * smoothed_kl + 0.3f * raw_kl;
const float kl = smoothed_kl;
prev_loss = stats.loss;
if (kl > kl_targ_ * 4) {                    // kl_targ_ = 0.05 -> 阈值 0.2
    lr_multiplier_ /= 1.5;
} else if (kl > kl_targ_ * 2 && lr_multiplier_ > 0.1) {   // 阈值 0.1
    lr_multiplier_ /= 1.5;
} else if (kl < kl_targ_ / 2 && lr_multiplier_ < 2.0) {   // 阈值 0.025
    lr_multiplier_ *= 1.5;
}
```

### 1.2 三个独立错误

**错误 A：`|Δloss|` 不是 KL。**
KL 散度是**两个概率分布之间的距离**（AlphaZero 原版用的是新策略与旧策略在
同一批状态上的动作分布 KL）。这里用的是**相邻两次更新之间交叉熵损失的变化量**。
两者量纲不同、语义无关：loss 的绝对变化量取决于 batch 组成、数据来源
（自对弈 or 人类棋谱）、模型当前置信度，唯独不反映"策略分布移动了多少"。

**错误 B：阈值与量纲不匹配 → 永远偏"过大"。**
训练早期 loss 从 ~5.4（均匀分布）向 3.2 下降，单批变化 0.05~0.12 是常态。
而阈值是 0.1 和 0.025。于是判定结果几乎是必然的"KL 过大 → 降学习率"，
偶尔"KL 正常 → 不动"，**极少**触发"KL 过小 → 升学习率"。

**错误 C：每次更新都调整，没有冷却。**
`policy_update()` 每批调用一次（`train.cpp:213`），每次跑 `epochs_=5` 个
epoch，但只是**在所有 epoch 结束后调整一次**。5 个 epoch 用同一个 `lr`
（`train.cpp:128-133`），这本身还算合理；问题在于 79 批就有 79 次调整机会。

### 1.3 实测证据（决定性）

30 批训练，每批记录 `kl` 和 `lr_multiplier`：

```
batch  1  kl:0.05000  lr_multiplier:1.000   loss:3.3527
batch  2  kl:0.08279  lr_multiplier:1.000   loss:3.1934
batch  3  kl:0.08148  lr_multiplier:1.000   loss:3.2718
batch  4  kl:0.05979  lr_multiplier:1.000   loss:3.2627
batch  5  kl:0.04354  lr_multiplier:1.000   loss:3.2683   [val] top1_acc:0.303
...
batch 10  kl:0.08972  lr_multiplier:1.000   loss:3.3271   [val] top1_acc:0.310
...
batch 20  kl:0.06220  lr_multiplier:1.000   loss:3.2932   [val] top1_acc:0.316
...
batch 25  kl:0.08325  lr_multiplier:1.000   loss:3.3271   [val] top1_acc:0.301
batch 26  kl:0.11246  lr_multiplier:0.667   loss:3.1465   <-- 越过 0.1, 降
batch 27  kl:0.10748  lr_multiplier:0.444   loss:3.2424   <-- 连续越线
batch 28  kl:0.12121  lr_multiplier:0.296   loss:3.3956
batch 29  kl:0.10754  lr_multiplier:0.198   loss:3.4712
batch 30  kl:0.10913  lr_multiplier:0.132   loss:3.3584   [val] top1_acc:0.330
```

注意第 26-30 批的**正反馈死亡螺旋**：

```
lr 变小 -> 单步更新变小 -> loss 变化反而变大(因为偏离最优, 抖动增大)
        -> |Δloss| 变大 -> 判定"KL 过大" -> lr 再变小 -> ...
```

`kl` 从 0.083 跳到 0.112 之后连续 5 批都在 0.10 以上，
`lr_multiplier` 从 1.0 → 0.667 → 0.444 → 0.296 → 0.198 → 0.132，
**每批正好 ×1/1.5**，一次都没有回升。

按同样速率，79 批（README 的推荐配置）会一路撞到 `lr_multiplier = 0.01` 下限
（`train.cpp:151`），即 `lr = 2e-3 × 0.01 = 2e-5`，**学习实质停止**。

### 1.4 这是否解释了"参数量不足"的体感

是的，而且是叠加的。325,964 参数本来就少，再配上末段 2e-5 的学习率，
参数**既没有容量、也没有步长**去改进。这就是为什么训练看起来"训不动"。

### 1.5 修复方向

1. **删掉这段伪 KL**，换成真正的 KL：在固定的验证集上，用更新前的策略
   `p_old` 和更新后的策略 `p_new` 计算 `mean(Σ p_old · (log p_old − log p_new))`。
   代价是需要多跑一次前向（`validate()` 已经在跑前向了，可以复用）。
2. **加冷却**：每 N 批才允许调整一次（例如 `check_freq_`），并且单批最多调整一档。
3. **改用标准做法**：如果懒得做真 KL，就直接用固定学习率调度
   （前 2/3 批恒定，后 1/3 批线性衰减），不要用反馈控制。反馈控制对噪声
   极度敏感，AlphaZero 原版的 KL 自适应是配合真实的、低方差的 KL 估计使用的。

## 2. 【P0】`--mix-ratio 0.5` 的语义陷阱与 one-hot 污染

### 2.1 实测的数字

```
[train] mix data loaded: 691640 train + 36402 val samples (data/mix_data*)
```

而自对弈数据的规模（同一批日志）：

```
batch i:1/8, samples:1338, buffer:1338
batch i:4/8, samples:1614, buffer:5654
batch i:8/8, samples:1500, buffer:10000   <-- 撞上 --buffer 10000 上限
```

### 2.2 混合数据的利用率只有 3%

```
每批优化 batch_size=512, mix_ratio=0.5  ->  自对弈 256 + 混合 256

自对弈: 池 10000 条, 每批抽 256
        每个样本每批被抽中概率 256/10000 = 0.0256
跑满 79 批: 累计消费 79×256 = 20,224 条
        池 10,000 条 -> 平均每条被消费 2.0 次

混合:   池 691,640 条, 每批抽 256
        每个样本每批被抽中概率 256/691640 = 3.7e-4
跑满 79 批: 累计消费 20,224 条
        池 691,640 条 -> 平均每条被消费 0.03 次   <-- 97% 的数据从未被看到
```

**注意这里不要误读成"混合数据权重不足"。** 每批损失里两类各占 50%，
权重是均衡的。真正的问题是**覆盖效率**：69 万条人类棋谱在 79 批里只用到 3%，
同时 1 万条自对弈样本被反复消费 2 次。

### 2.3 one-hot 让问题变成负面的

人类棋谱的目标是 one-hot（`tools/parse_renjunet.py:76` `p[moves[k+1]] = 1.0`），
实测熵 **0.000 nats**，每个样本恰好 1 个非零项。

把 one-hot 放进交叉熵，等价于告诉模型：
**"这个局面只有这一步是对的，其余 224 个位置概率必须是 0"**。

但人类棋谱里大量着法并非最优（`parse_renjunet.py` 只过滤了
`rule=1`、`swap`、`≥10 手`，没有任何质量筛选）。于是模型在
**逼近人类数据的噪声**，而不是在学习正确性。

更糟的是它与自对弈目标（MCTS 访问分布，软、多峰）混在同一批里：
- 混合数据说："只能下 A"
- 自对弈数据说："A 55%、B 25%、C 20%"
- 模型被迫取折中，两个都拟合不好

### 2.4 修复方向

1. **给人类棋谱做标签平滑**：`p = 0.9 * onehot + 0.1 * uniform`，
   或退一步用 `0.95/0.05`。这一行改动就能消除 one-hot 的极端梯度。
2. **按覆盖决定 mix_ratio**：如果希望 69 万条数据在 79 批内至少看一遍，
   需要 `n_mix ≈ 691640/79 ≈ 8754`，即 `mix_ratio` 要接近 **0.94**，
   batch_size 要更大。或者干脆**预训练阶段单独跑**（用混合数据预训练，
   再用纯自对弈微调），而不是混在同一个 batch 里。
3. **质量筛选**：至少过滤掉明显劣势的着法（用现有网络评估打分），
   或只保留棋谱中"网络评估为合理"的一手。

## 3. 【P1】缺少 Dirichlet 根噪声与温度调度

### 3.1 Dirichlet 噪声：完全没有

全仓搜索 `dirichlet` / `noise` 无任何命中。AlphaZero 的根节点噪声是
自对弈探索的核心机制：

```
P(a) = (1-ε)·p_θ(a) + ε·Dir(η)      ε ≈ 0.25, η ≈ 0.03 (围棋)
```

没有它，MCTS 完全跟随网络先验，**先验错就一路错**，自对弈对局高度重复，
产生的训练数据多样性不足。这也是为什么"参数量不足"会被放大——
数据的信息量本身就不够。

### 3.2 温度：始终是 1.0，没有调度

```cpp
// main.cpp:66-67
Trainer trainer(net, playout, batch_games, n_threads, 5.0f, 1.0f, ...);
//                              c_puct^  temp^  两者都是硬编码常量
```

而且 `cmd_train` 根本没有解析 `--temp` / `--c-puct` 参数
（`main.cpp:38-56` 的参数循环里没有这两个）。

标准做法是**前 N 手高温（τ=1）、之后低温（τ→0）**：

```
便宜但有效的近似: temp = (move_number < 30) ? 1.0 : 0.5
```

当前恒定 τ=1 导致：开局阶段访问计数差距被 `visits^(1/1)` 直接放大，
而实测 MCTS 根子节点访问数差异很大，采样会强烈偏向最优着法，
开局多样性不足。附带的证据是 `selfplay.cpp:758-780` 里那段
`temp <= 1e-6` 的 argmax 分支**永远走不到**（因为 temp 恒为 1.0），
是死代码。

### 3.3 修复方向

```cpp
// 1) 根节点加噪声 (expand_leaf 之后, 在 probs 计算之前)
//    对 root 的 child prior 做: prior = (1-eps)*prior + eps*dirichlet(gamma)
//    eps=0.25, gamma 对五子棋可取 0.15~0.3 (候选数少, 分布要更集中)

// 2) 温度调度
const float temp = (game.board.move_count() < 30) ? 1.0f : 0.5f;

// 3) 把 c_puct / temp 参数化, 便于调参
```

## 4. 【P1】`MAX_CAND=40` 把 82.5% 的位置训练成"绝不可下"

### 4.1 机制

```cpp
// selfplay.cpp
constexpr int MAX_CAND = 40;                                    // line 28

// expand_leaf (line 356-361)
const int keep = std::min<int>(MAX_CAND, candidates.size());
std::partial_sort(candidates.begin(), candidates.begin() + keep, ...);

// 采样时 (line 789-793)
std::array<float, BOARD_CELLS> probs{};
for (int i = 0; i < root.child_count; ++i) {
    const GNode& child = games[gi].nodes[root.child_begin + i];
    probs[child.action] = weights[i] / weight_sum;   // 其余位置保持 0
}
```

**根节点子节点数 ≤ 40，其余位置的目标概率恰好是 0。**

### 4.2 在真实棋谱局面上实测

用 `data/mix_data_states.bin` 的 600 个真实局面（平均 33.8 手）：

```
平均空格数（= 合法着法数）        191.2
其中"邻近"空格（半径2）            85.3
远离棋子群的空格                  106.0

MCTS 根节点子节点数 = min(40, 邻近空格数)
  实测平均                        39.4
  => 目标分布中概率恰为 0 的位置    185.6 / 225 = 82.5%

分阶段:
  布局(0-20子)  邻近空格  53.4  根子节点 38.4  零概率位置 186.6 (82.9%)
  中盘(20-40子) 邻近空格  89.1  根子节点 40.0  零概率位置 185.0 (82.2%)
  后盘(40+子)   邻近空格 113.0  根子节点 40.0  零概率位置 185.0 (82.2%)
```

### 4.3 为什么这是错的

那 106 个"远离棋子群"的空格**是合法着法**。五子棋里远距离落子
（扩展势、控制外线、做双三的远程连接）是正常手段。
但训练目标告诉策略头：**这些位置的概率必须是 0**。

后果有三层：

1. **直接错误监督**：模型被训练成给合法着法输出极端负 logit。
2. **泛化被破坏**：这些位置在 225 维输出里对应的行/列（约 82.5%）
   只在"被标零"这一个方向上被训练，从未学到"什么局面下这里其实是好棋"。
   这恰好和第 1 份分析里 `act_fc1` 有 70% 输入恒零的问题**互为因果**。
3. **MCTS 无纠错机会**：`candidates` 按网络先验排序后硬截断到 40
   （`selfplay.cpp:356-361`）。如果网络先验在某一步错了，
   正确着法会被直接丢弃，MCTS 连搜索它的机会都没有。
   这是"先验错了就永远学不回来"的闭环。

### 4.4 修复方向

```cpp
// 方案 A (最小改动): 对未被 MCTS 访问的位置做标签平滑
//   在生成 probs 时, 把剩余的 0 改成一个小常数, 再归一化
const float eps = 0.05f;                      // 或按 nearby/全部 比例动态定
for (int m = 0; m < BOARD_CELLS; ++m)
    probs[m] = probs[m] * (1.0f - eps) + eps / BOARD_CELLS;

// 方案 B (更正确): 参考 AlphaZero 的完整动作空间做法
//   不截断 candidates, 而是把 prior 为 0 的合法着法也纳入根节点
//   (候选数 225 对 400 playout 来说不是问题)

// 方案 C: 至少把 MAX_CAND 提到 60-80, 并用 GOMOK_MAX_CAND 环境变量可调
```

**注意方案 A 有个副作用**：它也会把"已经输了的位置"变得不像零。
所以更好的做法是区分"未探索"和"已判定为差"——
前者平滑，后者保持尖锐。

## 5. 【P1】验证指标不反映棋力

```cpp
// train.cpp:186-190
logger.log("[val] batch %d | val_loss:%.4f (pol:%.4f val:%.4f) | top1_acc:%.3f", ...)
```

### 5.1 问题

1. **数据源单一**：`validate()` 只跑 `mix_data` 的验证集
   （`train.cpp:158-191`，`n_val_` 来自混合数据）。它衡量的是
   "拟合人类 one-hot 的程度"，不是"下棋有多强"。
2. **top1_acc 指标本身不适合**：人类棋谱的一手是 one-hot，
   top1 命中率对"接近正确的第二选择"完全不奖励。
   一个棋力更强但风格偏离人类的模型，top1_acc 可能更低。
3. **验证集是顺序切分**：`train.cpp:56-64` 取前 `total/20` 作为验证集。
   实测 `mix_data` 严格按棋局分组顺序排列（相邻样本棋子数差 = +1 占 98.1%），
   所以验证集 = **最早的约 714 局棋**（36,402 样本 ÷ 平均 51 样本/局），
   训练集 = 之后的全部。这不是随机切分，有轻微分布偏差。

### 5.2 实测数据印证了"指标无意义"

```
[val] batch  5 | val_loss:3.7078 (pol:2.9421 val:0.7657) | top1_acc:0.303
[val] batch 10 | val_loss:3.7090 (pol:2.9408 val:0.7682) | top1_acc:0.310
[val] batch 15 | val_loss:3.7040 (pol:2.9458 val:0.7582) | top1_acc:0.306
[val] batch 20 | val_loss:3.6903 (pol:2.9244 val:0.7659) | top1_acc:0.316
[val] batch 25 | val_loss:3.7311 (pol:2.9559 val:0.7752) | top1_acc:0.301
[val] batch 30 | val_loss:3.6330 (pol:2.8637 val:0.7693) | top1_acc:0.330
```

**30 批训练，val_loss 从 3.708 到 3.633（改善 2.0%），
pol 从 2.942 到 2.864（改善 2.7%），val 从 0.766 到 0.769（无改善），
top1_acc 在 0.301~0.330 之间震荡，没有趋势。**

对比参考：均匀分布的交叉熵是 `ln(225) = 5.416`，
随机猜 top1 的命中率是 `1/225 = 0.44%`。
模型确实从随机学到了一部分（30% vs 0.44%），但**验证集上几乎没有进展**。

同一时间训练 loss 从 3.35 走到 3.36（同样无明确下降趋势），
但训练 loss 波动幅度（3.11~3.47）大于验证 loss，说明模型在训练集上
"记住"了一些东西而不泛化。**这正是过拟合+有效学习率不足的表征，
和第 1、2 节的结论一致。**

### 5.3 修复方向

1. **加真正的对局评估**：定期让新模型 vs 旧模型下 N 局（例如 20-40 局），
   报告胜率。这是唯一可靠的棋力指标。项目的 `evaluate_and_save`
   （`train.cpp:193-200`）目前只是**无条件保存**，没有任何评估。
2. **验证集随机切分**（或在 `npz_to_bin.py` 阶段就切好并打乱）。
3. 保留 `top1_acc` 但只作为"与人类吻合度"的参考，不作为模型选择依据。
4. **加最佳模型选择**：当前 `check_freq_` 每 50 批无条件覆盖
   `best_policy_<tag>_bin`，没有淘汰机制。至少保留 best + last 两份。

## 6. 【P2/P3】其余算法与工程问题

### 6.1 【P2】weight_decay 在两后端不一致

```cpp
// optimizer.h:11-14  — CPU 手写 Adam
Adam(double lr, double beta1 = 0.9, double beta2 = 0.999,
     double eps = 1e-8, double weight_decay = 0.0)      // <-- 默认 0，且无人传非零值

// network.cpp:633 — 构造时只传了 lr
PureNet::PureNet(double lr) : adam_(lr) { ... }

// network_cuda.cpp:84-85 — CUDA 后端用 PyTorch
optimizer = std::make_unique<torch::optim::Adam>(
    net->parameters(), torch::optim::AdamOptions(learning_rate));
    // PyTorch AdamOptions 默认 weight_decay = 0.01
```

- **CPU 训练：完全没有 L2 正则化。**
- **CUDA 训练：隐式有 0.01 的 weight decay。**

这意味着 README 里"CUDA 与 CPU 只有速度差异"的说法不成立——
两者训练的**目标函数不同**，会收敛到不同的解。325,964 参数 + 691,640
样本的组合本来就容易过拟合，缺 L2 会加重这一点。

修复：CPU 侧显式传入 `weight_decay`，CUDA 侧显式设 `AdamOptions(lr).weight_decay(wd)`，
并加 `--weight-decay` 参数统一控制。

### 6.2 【P2】梯度裁剪形同虚设

```
CPU  : adam_.clip_grad_norm(10.0f);                    // network.cpp:1141
CUDA : torch::nn::utils::clip_grad_norm_(..., 10.0);   // network_cuda.cpp:244
```

`max_norm = 10.0` 极其宽松。交叉熵对 logits 的梯度是 `(p - y)`，
元素绝对值 ≤ 1；325,964 个参数的梯度范数在正常训练中很少超过 10。
所以裁剪**几乎从不触发**，等于没有保护。

另外 CPU 侧的裁剪发生在 `scale(梯度, 1/B)` **之后**（`network.cpp:1127-1141`），
语义上是对的（裁剪应该在平均梯度上做），但配合"永不触发"的上限，
保护作用为零。建议降到 1.0~5.0。

### 6.3 【P3】无数据增强（棋盘 8 重对称性完全没用）

15×15 棋盘有 8 种对称变换（4 旋转 × 2 镜像）。对 (state, policy, z) 三元组
做同样变换是完全合法的数据增强，**样本效率直接提升 8 倍**。
全仓搜索无任何 rot/flip/transpose 相关代码。

对一个"参数量不足 + 数据量不足"的项目，这是性价比最高的一条改动之一。

### 6.4 【P3】`AsyncLogger` 是假的异步，且日志不落盘

```cpp
// logger.cpp:10-20 — log() 直接写 stdout 并 fflush，根本没进队列
void AsyncLogger::log(const char* fmt, ...) {
    ...
    std::fwrite(buf, 1, strlen(buf), stdout);
    std::fputc('\n', stdout);
    std::fflush(stdout);
}
```

- `queue_` / `cv_` / worker 线程（`logger.cpp:22-37`）是**死代码**，
  构造函数仍然起一个线程空转（每 50ms 轮询），纯浪费。
- `log()` 每条都 `fflush`，在几千条日志的场景下会锁 stdout。

**更严重的是：日志只到 stdout，项目里没有任何 `.log` 文件。**
本次分析要拿训练曲线，只能重新跑实验——之前所有训练的信息都丢失了。
建议至少支持 `GOMOK_LOG_FILE` 环境变量做 tee。

### 6.5 【P3】混合数据全量载入内存

```cpp
// train.cpp:47-64 — 一次性读入 3 个文件，然后切分
std::vector<float> all_s, all_p, all_w;   // 2.6GB + 0.65GB + 2.9MB ≈ 3.3GB
val_states_.assign(all_s.begin(), ...);   // 又复制一份
mix_states_.assign(all_s.begin() + ..., all_s.end());  // 再复制一份
```

峰值内存 ≈ `all_s`(2.6GB) + `val_states_`(0.17GB) + `mix_states_`(2.4GB) ≈ **5.2GB**，
而 `all_s` 随后才析构。对 8GB 显存 + 32GB 内存的笔记本还能接受，
但如果要扩大棋谱数据（第 2 节建议的方向），这里会先炸。

改进：先 seek 定位验证集范围，分开读；或改用 `memmap`。

### 6.6 【P3】`validate()` 的 chunk 缓冲区在循环内重复分配

```cpp
// train.cpp:158-191
void Trainer::validate(int batch_idx) {
    ...
    std::vector<float> lp(chunk * 225), val_out(chunk);   // 每次调用都分配
```

`chunk=512`，所以每次分配 `512*225*4 = 460KB`。每 5 批一次，影响很小，
但和 `policy_update()` 里每批分配 `s_buf`(1.8MB) + `p_buf`(460KB)
（`train.cpp:101-103`）是同一类问题。次要。

### 6.7 【P3】`--playout` 与节点竞技场的关系是隐式的

```cpp
// selfplay.cpp:431
const size_t arena_capacity = 1 + static_cast<size_t>(n_playout_) * MAX_CAND;
```

每个 game 预分配 `1 + playout × 40` 个 `GNode`。
`GNode` 是 `alignas(32)`，约 40 字节，所以 `--playout 400` 时
每局 16,001 节点 ≈ 640KB，`--batch-games 64` 时共 **41MB**。
可以接受，但改 `MAX_CAND`（第 4 节建议）时这里的隐含耦合需要同步，
否则会直接抛 `MCTS node arena exhausted`（`selfplay.cpp:370-371`）。

## 7. 需要澄清的 4 个"疑似但不是"的发现

分析过程中我核过下面 4 项，**它们都不是 bug**，记录在此避免重复排查：

### 7.1 ❌ `lr_multiplier_ < 2,0` 的逗号表达式 —— 我上一轮读错了

上一轮我口头提到 `train.cpp:146` 是 `lr_multiplier_ < 2,0`
（逗号表达式，永远为假）。**这是我的误读。** 逐字节确认：

```sh
$ sed -n '146p' src/train.cpp | cat -A
    } else if (kl < kl_targ_ / 2 && lr_multiplier_ < 2.0) {$
```

是 `2.0`，语法正确。同时我用
`grep -rnE "[<>=!]=? *[0-9]+ *,[0-9]+" src/ tests/ tools/*.py`
扫了全仓，没有任何逗号误写小数的地方。**上一轮那条说法作废**——
真正的 lr 问题在第 1 节（伪 KL），性质完全不同。

### 7.2 ❌ 卷积 padding 三端不一致 —— 实际一致

我怀疑 `export_onnx.py:19-21` 和 `network_cuda.cpp:16-18` 用 `padding=1`，
而 CPU 的 `conv3x3_forward`（`gradient.cpp:60-83`）用边界裁剪，
语义可能不同。用真实权重数值验证：

```
输入: 在 (0,0) 放一个子, 其余为 0
NumPy padding=1 : ch0(0,0)=-0.17580  ch0(0,14)=-0.00850  ch0(7,7)=-0.00850
C++ CPU fast    : ch0(0,0)=-0.17580  ch0(0,14)=-0.00850  ch0(7,7)=-0.00850
```

完全一致。C++ 的 AVX/scalar 路径（`row_begin/col_begin` 裁剪）**等价于
零填充 same padding**，`fast_conv3x3_relu`（`network.cpp:93-120`）
用 `std::fill(column, 0)` + `memcpy` 也是同一语义。三端一致，无问题。

### 7.3 ❌ 终局 value 符号传反 —— 实际正确

`select_leaf` 的终局分支：

```cpp
// selfplay.cpp:260-261
terminal_value = winner == 0 ? 0.0f
    : (winner == task.board.current_player() ? 1.0f : -1.0f);
```

用 `current_player()` 而非 `winner` 直接比较——对一个"刚走完、该对方走"的
局面，value 是**从"即将行动的一方"视角**给出的，与网络输出约定一致。
`backup_path` 逐层取反（`selfplay.cpp:117`）配合 `score = -q + ...`
（`selfplay.cpp:295`）也是自洽的。无问题。

### 7.4 ❌ `inference.cpp` 的 u64 头读取 u32 文件 —— 死代码

`src/inference.cpp:16` 的 `load_bin` 用 `uint64_t count`，而模型文件是
`uint32_t` 头（`network.cpp:619-620`）。如果这个文件参与编译，读
`conv1_weight.bin` 会把 `[0x480][0xBE07F539]...` 解释成 count=0xBE07F539480
并试图分配 3TB。

但 `CMakeLists.txt:41-49` 的可执行文件源文件列表里**没有 `inference.cpp`**，
全仓也无人 `#include "inference.h"`（`HandNet` 只有自引用）。
所以它**不参与编译**，不影响产物。属于"如果将来有人启用就会炸"的陷阱，
建议直接删除 `src/inference.cpp` / `src/inference.h`。

同理不参与编译的还有：`tests/bench_forward.cpp`、`tests/bench_torch.cpp`、
`tests/bench_train.cpp`、`tests/dump_forward.cpp`
（`build/dump_forward` 是旧产物，当前 CMakeLists 不生成）。

## 8. 修复优先级建议

| 顺序 | 改动 | 预计工作量 | 预期收益 |
|---|---|---|---|
| 1 | 删掉伪 KL，改固定 lr 调度（或真 KL + 冷却） | 0.5 天 | 解除学习率死亡螺旋 |
| 2 | 人类棋谱 one-hot 标签平滑（`0.9/0.1`） | 1 小时 | 消除极端梯度 |
| 3 | 根节点 Dirichlet 噪声 + 温度调度 | 0.5 天 | 自对弈多样性 |
| 4 | 未访问位置标签平滑（改 `MAX_CAND` 逻辑） | 0.5 天 | 消除 82.5% 的错误监督 |
| 5 | 棋盘 8 重对称数据增强 | 0.5 天 | 样本效率 ×8 |
| 6 | 真对局评估（新 vs 旧，N 局胜率） | 1 天 | 唯一可靠的模型选择依据 |
| 7 | 统一 weight_decay + 收紧 grad clip 到 1~5 | 2 小时 | CPU/CUDA 一致性 |
| 8 | 日志落盘 + 删死代码 | 2 小时 | 可观测性 |

**建议 1-4 一起做完再重新训练**，因为它们互相耦合：
没有多样化的自对弈数据（3），再好的学习率调度也学不出强策略；
而错误的监督信号（2、4）会让任何容量提升都被浪费。
